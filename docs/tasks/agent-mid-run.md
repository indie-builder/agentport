## 官方依据（2026-10-28）

已核对官方文档及安装的 `@anthropic-ai/claude-agent-sdk` 0.3.311 类型定义：

- [Streaming Input](https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode)：支持持续的 `AsyncIterable<SDKUserMessage>` 输入及运行中追加消息。
- [SDKUserMessage](https://code.claude.com/docs/en/agent-sdk/typescript#sdkusermessage)：`priority:'next'`（默认）在当前工具调用结束后同轮读取；若该轮先结束，则启动下一轮。不能把它表述为严格不跨轮。
- `priority:'later'` 等当前轮结束后再发送；`priority:'now'` 配合 `origin:{kind:'human'}` 可后台化能够移动的工作，否则中断当前轮。平台现有 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` 约束下的具体效果仍需实测。
- [Query](https://code.claude.com/docs/en/agent-sdk/typescript#query)：`interrupt()` 不等于取消全部排队消息，不应先中断再盲目重发；SDK `result` 表示一次 turn 结束，不等于整个 streaming query 结束。
- generator 将消息 yield 给 SDK 只证明交出消息，不能证明 CLI 或模型已消费。原轮 `result.user_message_uuids` 可提供消费证据，最多列出 64 项；hook 拒绝等路径仍需实际核验。

## 现有实现与真实缺口

- runner 当前输入生成器只 yield 首条用户消息；任务首行后的 stdin 已保持打开，但由问题通道读取，只处理 `question_response`。
- worker 已有问题持久化、DB 轮询、SSE 回放与取消通道，可复用对应模式；尚无追加用户输入协议或投递状态。
- 助手与工具消息在 run 收尾时批量保存。直接在 API 插入中间用户消息会造成历史顺序与 SDK transcript 不一致。
- 前端多处以“最后一条 user”为本轮起点，包含内容块定位、终态回填与分页恢复；增加运行中 user 消息必须同步调整。
- worker 当前首条 user 查询没有显式排序；若同一个 run 有多条 user，必须固定原始首消息身份。自动重试也需区分输入是否可能已经执行。

## 两轮设计校验结论

第一轮提出持久化投递状态、消息排序和自然收尾握手的完整设计。第二轮专门校验更小的候选：Redis 发布命令，runner yield 后 ACK，API 成功返回，再于 run 结束时保存消息。

**简化候选未通过，不能直接实施：**

1. yield ACK 不能当作模型已消费。收尾、取消、CLI 写失败或 hook 拒绝时，会出现接口成功但模型未应用的消息。
2. `next` 可以自动进入下一轮；关闭宿主输入队列撤不回已经交给 CLI 的消息，不能承诺严格同轮。
3. 超时不能统一返回确定的 409 并删气泡：消息可能已执行但 ACK 丢失。需区分明确拒绝与结果未知，重试复用同一 UUID。
4. 终态才保存会使 worker 崩溃丢失已确认输入。确认前必须留下可恢复的完整记录，不能只有 TTL 去重键；同时需检查同 UUID 正文一致性及保存确认结果。
5. 排序必须涵盖首条用户输入、助手块、tool_use、tool_result 和补充输入，并对应 transcript 顺序。只给补充用户行加合成时间不足以保证 fork 前缀正确。
6. 前端必须改用 run 身份或原始首消息身份划定本轮，跨标签页按稳定输入身份去重，终态以权威历史收口。
7. worker 提交输入时必须再次裁决停止状态：停止先处理则拒绝，提交先发生则保留真实投递结果，不能由 API 的早期检查代替。

无需因此直接采用完整 DB-first 架构；新增 `messages.sequence`、通用 `inputState`、跨轮队列或平台 `end_input` 都仍是候选，尚未固定。最低要求是可恢复确认记录、未知结果语义、实际消费证据、正确排序及重试/恢复边界。

## 建议实施方向（待验证）

- 首版只提供“补充指令（next）”，保留独立停止按钮；明确说明当前工具结束后读取，不能承诺立即抢占或严格不跨轮。
- 新增运行输入接口，使用每次发送意图唯一的 `clientMessageId`；不复用创建新 run 的 `/api/chat`。协议、确认状态及持久化方式仍待固定。
- 单一 stdin 分发器统一处理问题回答和追加用户消息，避免两个消费者抢读；可关闭输入队列须在 EOF、abort、异常与收尾时唤醒等待者。
- 追加消息带稳定 SDK UUID、`origin:{kind:'human'}`、`client_composed:true`，不拼接成另一套平台执行循环。
- 暂不实现 now/later 选择器、运行中附件/成果引用/OpenUI 动作、消息编辑或撤回。自然结束时已接受输入如何处理，须先经真实 SDK 探针确认再决定。
- 多 result 的累计成本、resume/fork 基线以及 `num_turns` 统计需核验；不在缺少实测时顺带改写当前运行成本口径。

## 后续验收要求

这些是实施前需要完成的验证，不代表已执行：

- 受控阻塞 MCP 工具运行中发送随机标记的 next 消息；释放工具后核对原轮消费 UUID、实际输出、同 run/session 与 transcript 中唯一输入。
